## 今日核心判断

**不要把“模型看到的工具描述”当成授权，也不要把“客户端收到的流式事件”当成业务执行的唯一事实。** 在截至北京时间2026年11月2日08:00的约24小时独立检索中，未找到足以核实为P0的全新正式产品、协议标准或经过独立复现的生产规模突破。本期因此采用**一项当期规范讨论 + 一组前期稳定版工程证据**的方式，观察两个长期耦合问题：工具调用前的可信权限判断，以及中断/恢复后的事件与副作用一致性。

这是研究判断，不是厂商宣布了统一新架构。对百万用户Cloud Agent而言，真正需要建立的是不依赖模型善意的 **Policy Enforcement Point（授权决策点）** 和不依赖单条SSE连接的 **Execution Ledger（执行账本）**。二者都应由确定性服务持有，模型只负责提出候选动作。

## 一、当期信号：MCP工具注解的信任边界仍需实现者谨慎处理

**事实与日期。** 2026年11月1日，Model Context Protocol规范仓库出现开放Issue #3492，讨论在客户端限制可选工具或强制工具选择时，如何解释不可信服务端的工具注解（尤其是 `readOnlyHint`、`destructiveHint`）。该Issue**只是社区提出的规范澄清请求**，不是正式SEP、已合并规范修订、安全漏洞公告或新的GA能力。原文：https://github.com/modelcontextprotocol/modelcontextprotocol/issues/3492 。

**一手规范交叉核对。** MCP 2026-07-28 Tools规范说明，工具列表可以依据**每次请求所呈现的授权**而不同，且工具注解在来自不可信服务器时不可作为可信安全判断。规范还建议让用户能够确认操作。这里的安全含义是：即使模型界面显示“只读”，实际服务端仍须按身份、资源、操作和策略版本执行授权；不可信MCP服务器给出的提示不能授予任何额外能力。原文：https://modelcontextprotocol.io/specification/2026-07-28/server/tools 。

**机制与反证。** 若客户端强制模型在若干工具中选择一项，不能仅凭第三方服务器声称“只读”就把它放入自动执行白名单。反过来，保守地视未受信工具为潜在写操作，会提高人工审批负担与任务延迟。对受控内网工具，平台可以通过经审计的注册表覆盖声明；但必须确保该覆盖来源可信、可追溯，不能回写成服务端自证。Issue讨论尚未形成正式标准，不应在技术选型中当作既定互操作保证。

**工程结论。** 工具发现与执行必须双重鉴权：`tools/list`按用户授权过滤可见能力，`tools/call`对真实操作再次做服务端校验。身份上下文包括 `tenant_id`、`principal_id`、`agent_id`、`task_id`、`resource_scope`、`policy_version`，均由可信控制面签发而非由模型填入。

## 二、前期稳定版的延续证据：LangGraph修复了“暂停不等于失败、重连不等于重跑”的细节

**版本日期要分清。** LangGraph Python 1.2.19、SDK 0.4.11及SQLite checkpoint 3.1.3发布于GitHub页面标注的**2026年10月30日**，并非今天的新发布。官方发布说明分别涉及：暂停工具不再被错误报告为失败；嵌套图消息/工具事件命名空间调整；异步任务在流式返回时保留正确结果；SDK的SSE游标、Last-Event-ID、重连退避与取消/等待接口修复。原文：https://github.com/langchain-ai/langgraph/releases 。

**架构意义。** 用户在网络断开时可能只丢失了事件，而任务仍在后台执行；工具因人工审批暂停时，也不应被记作不可恢复的业务失败。事件传输状态、任务状态和外部副作用是三种不同对象：重连SSE只应补齐已产生的事件，不应自行重发扣款、发邮件、修改文件等非幂等操作。仅凭SDK修复记录，不能证明框架具备端到端exactly-once业务语义、跨进程恢复SLA或多租户隔离。

**可实施的执行账本。** 每个工具副作用在调用前写入 `operation_id`、`idempotency_key`、调用者授权版本与期望资源版本；外部执行后记录结果与可审计回执。客户端重连使用单调事件序列或可验证游标回放；服务端恢复时根据账本区分“未发出”“已发出结果未知”“已确认完成”，对结果未知操作优先查询下游状态，而不是盲目重试。

## 三、主流路线与Tradeoff

| 路线 | 优点 | 代价和待证实问题 |
| --- | --- | --- |
| MCP Registry + Policy Gateway | 工具发现、权限过滤、调用审计可统一 | 需处理动态权限撤销、注册表信任根与中心网关尾延迟 |
| LangGraph类持久化编排 | Checkpoint、暂停/恢复和事件流有成熟抽象 | 业务幂等、外部系统事务、会话隔离仍须应用自己负责 |
| 托管microVM Session Runtime | 会话内执行隔离、端口映射与弹性管理可托管 | 运行时更新、会话失效、跨区域与状态持久性边界不能忽略 |
| 自建控制面 + 可替换Sandbox | 授权、成本、审计与计算后端可独立演进 | 实现和维护复杂度高，必须自建故障注入与容量测试 |

这些路线并非相互排斥：**Harness编排意图、Gateway执行策略、Runtime承载计算、Ledger记录不可抵赖的业务状态**。最危险的架构捷径，是让模型输出的“我已经执行成功”直接成为系统账本。

## 四、标准、研究与7/30天趋势雷达

**标准边界。** MCP规范允许基于请求授权过滤工具目录，但没有因此替代应用级RBAC/ABAC、工具结果验证或外部业务事务。11月1日的Issue是规范澄清讨论；截至本次核验未见其成为正式标准修订。没有找到可信的当期A2A正式版本、RSI可复现生产突破，故不为其虚构新增结论。

**7天：** 工具治理**加强（有限证据）**：近期身份/工具注册表实践与本期MCP信任边界讨论方向一致；流式恢复与事件语义**加强**：10月30日LangGraph修复说明真实工程边缘条件持续被处理。**30天：** Durable Execution独立控制面仍为**待证实**：缺少跨厂商同口径恢复时间、重复副作用率和成本数据；Agent RSI**待证实**：缺少可复现、长期净收益证据；Sandbox可移植性**待证实**：不同后端网络、权限与磁盘语义尚难等价。没有足够一手反证推翻既有假设，也没有足够新证据正式升级仓库长期趋势台账。

## 五、百万用户Cloud Agent的可执行建议

**第一优先级：工具权限契约。** 对100个混合可信/不可信MCP工具构建测试集，覆盖未声明注解、伪造只读、权限中途撤销、跨租户资源ID注入、同一任务内先读后写。要求每次实际工具调用均由可信服务端拒绝越权，且拒绝日志保留`principal/task/operation/policy_version`；不要把“模型没有尝试越权”当作验收。

**第二优先级：恢复与重连契约。** 对SSE断线、Gateway重启、Sandbox迁移、用户取消和人工审批暂停进行故障注入。分别测量事件重复/丢失、任务恢复时延、外部操作重复率和“未知结果”操作数量；对扣费、文件删除、消息发送采用可查询回执或幂等键。目标是建立可验证的SLO基线，**此处不预设未经测试的p99或零重复数字**。

**第三优先级：成本与授权联动。** 在每次工具执行前验证预算预留、租户配额和权限版本；恢复时重检撤销状态，取消后禁止后台工具偷偷继续运行。按每个成功任务的真实成本、失败重试成本与人工审批延迟做三维评估。
