## 今日核心判断

多 Agent 的价值不能由并发数量证明，Sandbox 的安全性也不能由后端名称证明。平台应将执行隔离、应用访问路径与协作收益分别作为可测试契约。北京时间11月27日08:00至28日08:00的有限独立检索未确认新的P0正式交付；以下为近期补充核验，不冒充今日新品。

## 近期进展与证据边界

**OpenShell v0.1.10（北京时间11月24日23:12，正式版本）**：官方升级说明显示 Kubernetes Helm 部署默认关闭经 Gateway 的 Sandbox 服务转发，而其他部署后端默认值不变；应用访问地址与 Gateway 连接分离。镜像仓库及 Helm Chart 也迁移至 Quay，最低测试 Kubernetes 版本为1.33。对平台而言，升级不仅是替换镜像，还可能改变访问拓扑、网络策略和镜像供应链。官方版本说明不等于独立安全审计，也不能证明不同后端具有相同隔离强度。

**Hugging Face 多 Agent 实验教程（官方页面11月26日，RSS对应北京时间08:00）**：作者提出在相同 token 预算下比较独立尝试、单 Agent 与通信协作，使用四个 Agent 的简单可验证任务演示训练。关键是区分额外采样与协作的边际收益。该教程是研究探索，不是生产级多 Agent 性能证明；简单任务上的结果不能外推到开放式代码或办公任务。

## 架构路线与 Tradeoff

| 路线 | 优势 | 代价 |
|---|---|---|
| Kubernetes Sandbox | 复用调度、配额与声明式管理 | 网络和存储策略随版本及部署方式变化 |
| 独立执行后端 | 隔离边界与生命周期可独立设计 | 镜像、快照、网络能力需要适配 |
| 多 Agent 并行 | 可增加搜索广度 | 额外模型成本、协调延迟与共享状态风险 |

建议统一生命周期接口，但显式暴露后端能力差异；不要把最弱后端的语义包装成所有后端的安全保证。

## 百万用户 Cloud Agent 工程建议

1. 建立 Sandbox Capability Manifest，记录隔离类型、网络入口出口、持久卷、快照、镜像摘要与策略版本；不满足任务最低要求时拒绝调度。升级测试覆盖服务转发关闭、旧镜像与新控制面混用、私有镜像镜像源失效。
2. 将应用访问与管理控制面分开，针对租户身份、短期访问凭证、撤权及 WebSocket 连接建立独立测试；禁止因后端切换静默放宽网络策略。
3. 建立等预算协作评测：单 Agent、独立并行、通信协作三组使用相同模型和总 token/时间上限；记录成功率、单位成功任务成本、P95 延迟、重复工作率与越权事件。只有协作收益覆盖协调成本时才启用多 Agent。
